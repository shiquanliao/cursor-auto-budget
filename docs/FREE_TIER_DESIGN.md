# 免费体验层设计

## 目标

免费体验的目标不是让用户永久免费，而是用一个可控成本完成三件事：

1. 用户真的完成安装；
2. 用户真的跑通至少一个有价值的任务；
3. 用户理解消耗规则，并愿意继续使用或付费。

## 首发参数

系统内部换算：`500,000 quota = $1`。

| 事件 | 奖励 quota | 美元价值 | 发放条件 |
|---|---:|---:|---|
| 完成注册 | 250,000 | $0.50 | 完成基本账号验证 |
| 完成安装 | 750,000 | $1.50 | 安装凭据成功兑换 + 客户端首次连接 |
| 每日签到 | 25,000–75,000 | $0.05–$0.15 | 每自然日一次，服务端幂等 |
| 连续 7 天 | 250,000 | $0.50 | 7 个不同自然日均签到 |
| 邀请人奖励 | 250,000 | $0.50 | 被邀请人累计真实消费达到 250,000 后 |
| 被邀请人奖励 | 100,000 | $0.20 | 完成安装后 |

### 用户侧文案

不要写“无限”“永久”“固定 20 次”。建议写：

> 注册先得 $0.50，完成安装后合计 $2 免费体验额度。按近期真实用量估算，约可完成 1 次常规任务或 6 次轻量任务；长上下文和多轮工具调用会增加实际消耗。

## 为什么不是注册直接送 $2

把主奖励放在“安装成功”之后，可以显著提高获客质量，也降低脚本批量注册的收益。注册奖励只需要覆盖一次轻量体验，主奖励应对应一个真实激活动作。

## 现有系统如何映射

当前 new-api 已经具备：

- `QuotaForNewUser`：新用户默认额度；
- 每日签到开关和随机 `MinQuota` / `MaxQuota`；
- 邀请人与被邀请人奖励字段；
- 默认 API Token 自动生成。

第一阶段可以直接设置：

```text
QuotaForNewUser = 250000
CheckInEnabled = true
CheckInMinQuota = 25000
CheckInMaxQuota = 75000
QuotaForInvitee = 0
QuotaForInviter = 0
```

邀请奖励先保持为 0。现有邀请奖励如果在“完成注册”时立即到账，容易被批量小号利用；等“真实消费后发奖”落地后再开启。

安装奖励、连续签到和有效邀请建议使用独立的 `promotional_grants` 奖励账本，不要只直接修改 `users.quota`。建议字段：

```text
id, user_id, event_type, event_key, quota,
status, expires_at, created_at, granted_at
```

其中 `(user_id, event_type, event_key)` 必须唯一，保证重试不会重复发奖。

## 免费次数如何展示

不要使用固定次数。每天从已完成的 `billing_transactions` 中计算：

- 轻量：近 7 天单次结算 p25；
- 常规：近 7 天单次结算 p50；
- 深度：近 7 天单次结算 p75；
- 单档最少需要 30 条样本，样本不足就显示“数据积累中”。

计算公式：

```text
预计次数 = floor(当前可用赠送额度 / 对应分位单次结算额度)
```

页面必须同时显示“约”和“实际以任务长度为准”。

## 防刷规则

- 同一用户每日签到只能成功一次，数据库唯一键兜底；
- 同一设备 30 天内只触发一次安装奖励；
- 同一支付身份、手机号或可信登录身份限制新客奖励；
- 邀请奖励必须在被邀请人产生真实消费后发放；
- 每个邀请人每月最多奖励 5 个有效邀请；
- 单用户首 7 天赠送成本硬上限建议为 $3.50；
- 全站设置月度营销预算，达到 80% 告警，达到 100% 停止新发奖但不扣回已发奖励。

不要采集不必要的高风险设备指纹。防刷字段应最小化、设定保留期限，并在隐私政策中说明。

## 上线前门槛

当前计费资料显示存在单次实际结算高于预扣额度的情况。公开免费体验前必须保证：

1. 单次请求不能无界透支赠送余额；
2. 余额不足时用户能看到清晰提示；
3. 赠送余额与充值余额可区分，退款与过期规则明确；
4. 生产与法务门禁通过后，再把 GitHub 项目连接到真实注册入口。

在这些条件完成前，GitHub 项目只用于计算器、内测申请和需求验证。
